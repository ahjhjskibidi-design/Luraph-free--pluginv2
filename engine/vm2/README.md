# VM2 — Lua Virtual Machine

A register-based Lua 5.1+ interpreter written in JavaScript. Runs
compiled bytecode produced by `engine/compiler/`. Used by the
obfuscator pipeline to verify that generated bytecode is correct
before encryption and packaging.

## What it is

VM2 is a complete Lua interpreter. It executes bytecode from the
compiler, manages a call stack, handles metatables, coroutines,
protected calls, and provides the standard library.

It is not a bridge to real Lua, not a Lua-in-JS shim, and not a
"Lua-like" language. It reads the same bytecode the Roblox runtime
would run.

## What it is not

- **Not a compiler.** Uses `engine/compiler/` to translate source
  into bytecode.
- **Not a production runtime.** Designed for testing the compiler
  and simulating script behavior during obfuscation. It is slower
  than Roblox Luau by a factor of 10-50x.
- **Not a sandbox escape vector.** The VM cannot read files,
  execute processes, or access the host environment beyond what
  the standard library exposes.

## Architecture

```
+----------------------------------------+
|  VM2 (index.js)                        |
|  - Main dispatch loop                  |
|  - Instruction decoding                |
|  - Frame management                    |
+----------------------------------------+
            |              |
            v              v
+-------------------+  +-------------------+
|  Stack / Frame    |  |  Runtime          |
|  (stack.js)       |  |  (runtime/*)      |
|                   |  |                   |
|  - Registers      |  |  - Arithmetic     |
|  - PC             |  |  - Comparison     |
|  - Varargs        |  |  - Metatables     |
|  - Upvalues       |  |  - Tables         |
|  - Return slots   |  |  - Strings        |
+-------------------+  +-------------------+
            |              |
            v              v
+-------------------+  +-------------------+
|  Upvalue cells    |  |  Standard Library |
|  (upvalue.js)     |  |  (stdlib/*)       |
+-------------------+  +-------------------+
```

## Execution model

Every function activation is a **Frame**. Frames are stored in a
**Stack**. The main dispatch loop runs until the stack drops below
a target depth.

Each frame has:
- A **proto** — the compiled function metadata (instructions,
  params, upvalue list, register count).
- A **register file** — an array of values indexed by register
  number. Registers are allocated by the compiler, so the VM never
  needs to guess.
- A **program counter** (PC) — the index of the next instruction
  to fetch.
- **Varargs** — a list of extra arguments for functions declared
  with `...`.
- **Upvalue cells** — references to variables captured from the
  enclosing function.

### Instruction cycle

1. Fetch `instructions[pc]`
2. Increment `pc`
3. Decode the 32-bit word into `(op, A, B, C)`
4. Dispatch on the opcode
5. Repeat

The dispatch loop catches all exceptions, wrapping them in a
`VMError` with the current opcode and PC for easier debugging.

### Call/return protocol

A `CALL` instruction:
1. Reads the function from register A
2. Reads `nargs = B` arguments from registers A+1..A+B
3. If the function is a JS function, invokes it and writes
   results to registers A..A+nresults-1
4. If the function is a Lua closure, pushes a new frame with
   `returnBase = A`, `nresults = C-1`, and the arguments copied
   into the callee's parameter registers

A `RETURN` instruction:
1. Collects return values from registers A..A+B-2
2. Pops the current frame
3. Writes the values into the caller's registers starting at
   `returnBase`
4. If `nresults < 0`, the caller takes all return values

### Upvalues

Closures capture locals from their enclosing function. The VM
represents each captured variable as an `UpvalueCell`:
- While the enclosing function is on the stack, the cell holds a
  reference to the register in that frame.
- When the enclosing function returns, the cell "closes" — the
  register value is copied into the cell, and the reference to the
  frame is dropped.

Two closures that capture the same local share the same cell, so
writing through one is visible through the other.

## Supported Lua subset

### Language features

- Variables: locals, globals, upvalues
- Types: nil, boolean, number, string, table, function
- Operators: `+ - * / % ^ .. == ~= < <= > >= and or not #`
- Control flow: if/elseif/else, while, repeat/until, numeric for,
  generic for, break, return
- Functions: named, anonymous, varargs, recursion, closures
- Tables: array part, hash part, constructor syntax
- Metatables: all standard metamethods
- Coroutines: create, resume, yield, status, wrap, close
- Protected calls: pcall, xpcall, error
- Multiple assignment and multiple return values

### Standard library

- `base` — print, type, tostring, tonumber, pairs, ipairs, next,
  pcall, xpcall, error, assert, select, rawget, rawset, rawequal,
  rawlen, getmetatable, setmetatable, load, loadstring,
  collectgarbage
- `string` — len, sub, byte, char, rep, lower, upper, reverse,
  format, find, match, gmatch, gsub, dump
- `table` — concat, insert, remove, sort, maxn, pack, unpack,
  move, clear, clone, create, find, freeze, isfrozen
- `math` — full library including trig, log, random, clamp,
  sign, round, noise
- `os` — time, clock, date, difftime, getenv, exit, tmpname,
  remove, rename, execute, setlocale
- `io` — stdout, stderr, stdin, write, read, lines, open, close,
  flush, type, input, output
- `coroutine` — full library
- `debug` — getinfo, traceback, sethook, gethook, getlocal,
  setlocal, getupvalue, setupvalue, upvalueid, upvaluejoin,
  getmetatable, setmetatable, getregistry, getuservalue,
  setuservalue
- `bit32` — full library
- `utf8` — char, charpattern, codepoint, codes, len, offset
- `package` — loaded, preload, path, cpath, loaders, loadlib,
  seeall, searchpath, require

### Not supported

- `goto` / labels (Lua 5.2+)
- `_ENV` semantics (Lua 5.2+)
- Integer subtype (Lua 5.3+) — all numbers are JS doubles
- Binary chunk loading (`load` with a byte string)
- `string.dump` (throws an error)
- Real file I/O (all `io.open` calls fail)
- Native library loading (`package.loadlib` always fails)

## Usage

### Direct execution

```js
import { VM2 } from './engine/vm2/index.js';
import { compile } from './engine/compiler/index.js';
import { parse } from './engine/parser/index.js';

const ast = parse('print("hello")');
const program = compile(ast);
const vm = new VM2(program, {
  io: { print: (s) => process.stdout.write(s + '\n') },
});
vm.run();
// Output: hello
```

### Custom globals

```js
const vm = new VM2(program, {
  io: { print: console.log },
  globals: {
    myFunc: () => 42,
    MY_CONST: 'abc',
  },
});
```

The default globals are installed by `stdlib/index.js`. Any keys
you pass in `options.globals` are merged after installation, so
they can override standard library functions if needed.

### Attaching a compiler for loadstring

```js
import { parse } from './engine/parser/index.js';
import { compile } from './engine/compiler/index.js';

vm.setCompiler((source) => {
  const ast = parse(source);
  return compile(ast);
});

// Now loadstring works
const [fn] = vm.globals.loadstring('return 1 + 1');
console.log(vm.callAny(fn, [])); // [2]
```

### Limiting execution

```js
const vm = new VM2(program, {
  maxSteps: 100000,  // abort after 100k instructions
  maxDepth: 100,     // abort on deep recursion
});
```

### Disabling libraries

```js
const vm = new VM2(program, {
  libraries: {
    os: false,      // no os library
    io: false,      // no io library
    debug: false,   // no debug library
    package: false, // no require
  },
});
```

## Test suite

Run:

```bash
node engine/vm2/test.js
```

The suite covers 60 cases across arithmetic, comparison, control
flow, functions, closures, tables, strings, and the standard
library. A pass means the compiler produced correct bytecode and
the VM executed it correctly.

Failures usually indicate a compiler bug, not a VM bug. The
compiler decides register allocation, constant pool layout, and
jump offsets. If the bytecode is malformed, the VM's error messages
point to the opcode and PC where execution diverged.

## Performance notes

The VM is not optimized. It runs on V8's JIT and benefits from
JavaScript's speed, but:

- Every frame allocates a fresh register array.
- Every call pushes a frame object.
- Every arithmetic operation goes through a function call for
  metatable lookup.

For test workloads (script execution of a few thousand
instructions), performance is fine. For long-running scripts,
expect 10-50x slower than Roblox Luau.

If performance matters, consider:

1. **Inlining the runtime functions.** `luaAdd`, `luaSub`, etc.
   could be inlined into the dispatch loop, at the cost of code
   size.
2. **Caching metatable lookups.** A per-value metatable cache
   would avoid the `getMetatable` call on every arithmetic
   operation.
3. **Avoiding frame allocation.** A frame pool would let frames be
   reused across calls. This complicates the upvalue closing
   logic.

None of these are implemented. The VM prioritizes correctness
over speed.
